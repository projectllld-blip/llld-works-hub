## コード直書きが残る問題

商品・料金・CTAの情報が `data/contents.json` とJSに散ると、以下の問題が起きる。

- マーケットカードと購入確認ページで表示文言がズレる。
- 有料 / サブスクを誤って利用開始可能にするリスクが上がる。
- `利用開始`、`購入確認`、`β版を利用する`、`開発中` の条件が追いにくい。
- 商品追加時にHTML / JS / JSONの複数箇所を触る必要が出る。
- 将来の管理者mock画面で、何を管理対象にするかが曖昧になる。
- 決済実装前に、価格やCTAの正本がどこか分からなくなる。
- 本物管理者画面へ進むとき、DB化対象と画面表示専用ロジックの境界が曖昧になる。

## 比較した案

### A案: 既存 `data/contents.json` に寄せる

既存の `data/contents.json` を、商品・料金・CTA設定の短期的な正本候補として扱う案。

良い点:

- すでにマーケット、詳細、購入確認が参照している。
- `priceType`、`saleStatus`、`deliveryType`、CTA系項目が存在する。
- 新しいファイルを増やさず、現行構成と相性がよい。
- GitHub Pagesの静的構成のまま運用できる。
- v1.6cのmock管理画面へ項目を渡しやすい。

注意点:

- コンテンツ情報と商品設定が混ざる可能性がある。
- 表示用説明と管理用設定の境界をdocsで明確にする必要がある。
- 大きくなりすぎる場合、後で商品設定ファイルへ分離する余地を残す。

### B案: 新規 `data/products.json` を作る

商品・料金・CTAだけを新規JSONへ切り出す案。

良い点:

- 商品設定の責務が明確になる。
- 将来DB化するときの中間構造にしやすい。
- 管理者mock画面の入力項目を表現しやすい。

注意点:

- `contents.json` との重複が発生しやすい。
- `id` / `slug` / `app_key` の紐づけミスが起きる。
- 今回のv1.6bでは新規JSON追加が禁止されているため、実装しない。

### C案: 新規 `data/marketplace-products.json` を作る

マーケット販売用の商品設定だけを切り出す案。

良い点:

- マーケット表示専用の価格、CTA、掲載状態を管理しやすい。
- 社内ポータルや内部コンテンツと販売商品を分けやすい。

注意点:

- マーケット専用に寄りすぎると、購入確認、My Apps、管理者mockとの連携が二重管理になりやすい。
- 名前が示す範囲が狭いため、将来の購入後反映や管理者画面との接続時に再整理が必要になる可能性がある。
- 今回のv1.6bでは新規JSON追加が禁止されているため、実装しない。

### D案: 将来のSupabase `apps` / `plans` / `product_prices` 系DBへ移す

本物のDBで商品、料金、プラン、表示状態を管理する案。

良い点:

- 管理者画面から更新できる。
- 価格変更履歴、公開状態、決済連携と接続しやすい。
- 企業ごとの購入状態や利用開始状態と分離しやすい。

注意点:

- DB / RLS / migration / 管理者権限 / 管理者ロールが必要。
- 本番相当DBへのschema変更になるため、人間確認が必須。
- 価格変更履歴、誤操作防止、公開前確認がないまま進めると危険。
- v1.6b / v1.6cでは扱わない。

## 推奨方針

現時点では A案を推奨する。

短期方針:

- v1.6bではdocs整理のみ行う。
- 新規JSON、DB、RLS、migration、本体UI / JS / CSS変更は行わない。
- 次に実装する場合は、まず既存 `data/contents.json` の項目を正本候補として棚卸しする。
- 商品ごとの価格、状態、CTA、サムネイル、サポート対象、購入後 `app_key` を `contents.json` または既存データ構造へ寄せる。
- JS側に残すのは、安全判定、画面描画、フォールバック表示などのロジックに限定する。
- 商品ごとの差分文言やCTAは、できるだけデータ側へ寄せる。

中期方針:

- `contents.json` が肥大化し、コンテンツ情報と商品設定の責務が混ざりすぎた時点で、`products.json` などの静的商品設定ファイルを検討する。
- ただし、分離するときは `id` / `slug` / `app_key` の紐づけルールを先にdocs化する。

長期方針:

- 本物の料金編集DB、商品マスタ、料金マスタは v2.x 以降で扱う。
- その前に、管理者権限、管理者ロール、RLS、変更履歴、価格変更履歴、公開前確認、本番 / 検証分離、管理者のみ編集可能なpolicyを整える。

## 料金形態とCTAの基本ルール

v1.6b時点の基本ルールは以下。

| 料金形態 | 確認画面 | CTA候補 | 確認後の扱い |
|---|---|---|---|
| 無料 | 利用開始確認 | `利用開始` | `sessionStorage` 上の仮追加は可。正式な `app_instances` 反映はv1.7以降。 |
| β版 | β版利用確認 | `β版を利用する` | `sessionStorage` 上の仮追加は可。未完成範囲を明記する。 |
| 買い切り | 購入確認 | `購入確認` | 決済未実装中はポータル追加しない。 |
| サブスク | 購入確認 | `購入確認` | 決済未実装中はポータル追加しない。 |
| 開発相談 | 開発相談 | `開発を相談する` | 購入ではなく相談導線へ流す。 |
| 開発中 / 準備中 | 準備中 | `先行案内を受ける` / `開発中` | 購入・利用開始不可。 |

有料化前に無料で使わせたい商品は、有料ではなく、無料 / β版 / 無料トライアル相当として分類する。
